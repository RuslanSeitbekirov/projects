## 1. Немного теории

### 1.1. Архитектура через интерфейсы

Идея: сначала описываем **что** умеет каждая часть программы (интерфейсы), и только потом — **как** (классы).
Модули общаются только через интерфейсы, поэтому:

- **Слабая связанность.** `Store` (магазин) не знает про классы `Catalog`, `CardPayment` — только про `ICatalog`, `IPaymentMethod`.
- **Заменяемость.** Хотим оплату через СБП — пишем `SbpPayment : IPaymentMethod`, код магазина не трогаем.
- **Параллельная разработка.** Один программист пишет каталог, другой — оплату; договорились об интерфейсе — и работают независимо.
- **Тестирование.** В тестах вместо настоящей оплаты подставляется заглушка, реализующая тот же интерфейс.

### 1.2. Абстрактный класс в крупных приложениях (для отчёта, п. 2)

- **Интерфейс** описывает *роль/возможность* («можно скачать», «можно оплатить»). Класс может играть много ролей сразу.
- **Абстрактный класс** — *общая основа* родственных классов: хранит общие данные и код, а различия отдаёт наследникам через `abstract`-методы.
- Типичная схема: **интерфейс → абстрактный класс с общей реализацией → конкретные классы**. Внешний код зависит только от интерфейса.
- Принципы SOLID, на которые это опирается:
  - **D (Dependency Inversion)** — модули верхнего уровня зависят от абстракций, а не от конкретных классов (`Store` → `IPaymentMethod`);
  - **I (Interface Segregation)** — лучше несколько маленьких интерфейсов, чем один большой (`IProduct`, `IDownloadable` отдельно);
  - **O (Open/Closed)** — добавляем новый способ оплаты новым классом, не меняя старый код.

### 1.3. Понятия, которые показаны в коде

| Понятие | Где в коде |
|---|---|
| Наследование интерфейсов | `IBook : IProduct` |
| Абстрактный класс и абстрактный метод | `Product`, `Describe()` |
| Реализация интерфейса классом | `Product : IProduct`, `Catalog : ICatalog`, … |
| Множественное наследование интерфейсов | `EBook : Book, IDownloadable` (класс + ещё один интерфейс) |
| Явная реализация интерфейса | `string IDownloadable.Download()` |
| Внедрение зависимости через конструктор | `Store(ICatalog, IPaymentMethod)` |
| Полиморфизм | `Console.WriteLine(book)` вызывает разный `Describe()` |
| Частичная реализация | `CashPayment` не считает сдачу |

## 3. `Products.cs` — товары

### 3.1. Абстрактный класс `Product`

```csharp
1   namespace BookStore
7       public abstract class Product : IProduct
9           public string Title { get; }
10          public decimal Price { get; }
12          protected Product(string title, decimal price)
14              Title = title;
15              Price = price;
19          public abstract string Describe();
21          public override string ToString() => Describe();
```

- **стр. 7** — абстрактный класс, реализует `IProduct`. Хранит общие для всех товаров данные.
- **стр. 9–10** — **автосвойства только для чтения** (`get` без `set`): значение можно задать только в конструкторе, потом оно не меняется. Так реализуются свойства `Title` и `Price` интерфейса.
- **стр. 12** — конструктор `protected`: вызвать его могут только наследники (через `base(...)`). Создать `new Product(...)` всё равно нельзя — класс абстрактный.
- **стр. 14–15** — запоминаем название и цену.
- **стр. 19** — абстрактный метод: каждый вид товара описывает себя по-своему; тела нет, наследник обязан сделать `override`.
- **стр. 21** — переопределяем `ToString()` класса `object`. `=>` — **метод-выражение** (короткая запись `{ return Describe(); }`). Благодаря этому `Console.WriteLine(book)` печатает описание книги, а не имя типа `BookStore.Book`.

### 3.2. Класс `Book`

```csharp
25      public class Book : Product, IBook
27          public string Author { get; }
29          public Book(string title, string author, decimal price) : base(title, price)
31              Author = author;
34          public override string Describe() => $"{Author} — «{Title}», {Price} руб.";
```

- **стр. 25** — наследуется от абстрактного класса `Product` (получает `Title`, `Price`) и реализует `IBook` (добавляет `Author`). Сначала базовый класс, потом интерфейсы.
- **стр. 27** — свойство автора, только для чтения.
- **стр. 29** — `: base(title, price)` — **вызов конструктора базового класса**: название и цену сохраняет `Product`.
- **стр. 31** — сами сохраняем только автора.
- **стр. 34** — реализуем абстрактный `Describe()`; `$"..."` — интерполяция строк, в `{}` подставляются значения свойств.

### 3.3. Класс `EBook`

```csharp
41      public class EBook : Book, IDownloadable
43          public EBook(string title, string author, decimal price) : base(title, author, price) { }
47          string IDownloadable.Download() => $"Файл «{Title}.pdf» скачан";
49          public override string Describe() => base.Describe() + " [электронная]";
```

- **стр. 41** — электронная книга **является** книгой (наследует `Book`) и **умеет** скачиваться (`IDownloadable`). Класс может иметь только один базовый класс, но любое число интерфейсов — это и есть «множественное наследование интерфейсов».
- **стр. 43** — конструктор просто передаёт всё в конструктор `Book`; тело пустое `{ }`.
- **стр. 47** — **явная реализация интерфейса**: имя метода записано как `IDownloadable.Download`, модификатора доступа нет. Такой метод **нельзя** вызвать через переменную типа `EBook` (`ebook.Download()` — ошибка), только через интерфейс: `((IDownloadable)ebook).Download()` или `item is IDownloadable file` → `file.Download()`. Применяется, когда метод нужен только в роли интерфейса или когда два интерфейса имеют методы с одинаковыми именами.
- **стр. 49** — переопределяем `Describe()` ещё раз; `base.Describe()` вызывает версию из `Book`, к ней дописываем пометку.

### 4.1. `Catalog`

```csharp
8       public class Catalog : ICatalog
10          private readonly List<IBook> books = new List<IBook>();
12          public void Add(IBook book) => books.Add(book);
14          public IEnumerable<IBook> GetAll() => books;
16          public IEnumerable<IBook> FindByAuthor(string author) =>
17              books.Where(b => b.Author.Contains(author, StringComparison.OrdinalIgnoreCase));
```

- **стр. 8** — реализация каталога «в памяти». Завтра можно написать `DbCatalog : ICatalog`, работающий с базой данных, — магазин не заметит разницы.

- **стр. 12** — добавление в список.
- **стр. 14** — `List<IBook>` сам является `IEnumerable<IBook>`, отдаём как есть.
- **стр. 16–17** — `Where` (LINQ) оставляет только книги, у которых автор содержит подстроку. `b => ...` — **лямбда-выражение** (условие для каждой книги `b`). `OrdinalIgnoreCase` — без учёта регистра: «толстой» найдёт «Толстой».

### 4.2. `Cart`

21      public class Cart : ICart

27          public void Add(IProduct product) => items.Add(product);

- **стр. 23** — список товаров.
- **стр. 25** — свойство только для чтения (`=>` у свойства — короткий геттер). Список отдаётся как `IReadOnlyList`, поэтому снаружи у него нет метода `Add`/`Remove`.
- **стр. 27** — добавить товар.
- **стр. 29** — LINQ `Sum`: сложить `Price` всех товаров.

### 4.3. Способы оплаты

```csharp
33      public class CardPayment : IPaymentMethod
35          public string Name => "Банковская карта";
36          public bool Pay(decimal amount) => amount > 0;
40      public class CashPayment : IPaymentMethod
42          public string Name => "Наличные";
43          public bool Pay(decimal amount) => true;
```

- **стр. 33–36** — оплата картой; условно «успешна», если сумма положительная.
- **стр. 40–43** — оплата наличными — **частичная реализация** (задание разрешает): всегда успешно, сдача не считается.
- Два разных класса, один интерфейс — магазин может работать с любым из них.

### 4.4. `Store` — магазин

```csharp
51      public class Store
53          private readonly ICatalog catalog;
54          private readonly IPaymentMethod payment;
56          public Store(ICatalog catalog, IPaymentMethod payment)
58              this.catalog = catalog;
59              this.payment = payment;
62          public ICatalog Catalog => catalog;
```

- **стр. 53–54** — поля имеют типы **интерфейсов**. Ни одного `new Catalog()` или `new CardPayment()` внутри магазина нет.
- **стр. 56** — **внедрение зависимостей через конструктор** (Dependency Injection): нужные объекты создаёт и передаёт вызывающий код.
- **стр. 58–59** — `this.catalog` — поле, `catalog` — параметр с тем же именем; `this` их различает.
- **стр. 62** — открываем каталог наружу, но тоже как интерфейс.

```csharp
64          public void Checkout(ICart cart)
66              decimal sum = cart.Total();
67              bool ok = payment.Pay(sum);
68              Console.WriteLine($"Оплата {sum} руб. ({payment.Name}): {(ok ? "успешно" : "отказ")}");
71              foreach (IProduct item in cart.Items)
73                  if (ok && item is IDownloadable file)
75                      Console.WriteLine("  " + file.Download());
```

- **стр. 64** — оформление заказа; корзина тоже приходит как интерфейс.
- **стр. 66** — сумма через `ICart.Total()`.
- **стр. 67** — оплата через `IPaymentMethod.Pay()` — какой именно способ, магазин не знает.
- **стр. 68** — вывод; внутри интерполяции тернарный оператор взят в скобки, иначе `:` спутался бы с форматом.
- **стр. 71** — перебираем товары корзины.
- **стр. 73** — **сопоставление с образцом** `item is IDownloadable file`: если товар реализует `IDownloadable`, он сразу приводится к этому типу и кладётся в переменную `file`. Бумажные книги условие не пройдут.
- **стр. 75** — вызов `Download()` **через интерфейс** — именно так работает явно реализованный метод из `EBook`.

## 7. Важные моменты (вопросы на защите)

1. **Почему у `Store` поля типа интерфейса?** — Чтобы магазин не зависел от конкретных реализаций; новую оплату или каталог можно подключить без изменения `Store` (принцип инверсии зависимостей).
2. **Чем `IBook : IProduct` отличается от `Book : Product`?** — Первое — наследование *контракта* (требований), второе — наследование *реализации* (полей и кода).
3. **Почему `ebook.Download()` не компилируется?** — Метод реализован явно и доступен только через ссылку типа `IDownloadable`.
4. **Зачем `Product` абстрактный, если есть `IProduct`?** — Интерфейс задаёт требования, а абстрактный класс хранит общий код (`Title`, `Price`, конструктор, `ToString`) — наследникам не нужно повторять его.
5. **Зачем отдельный `IDownloadable`, а не метод в `IBook`?** — Бумажную книгу скачать нельзя; маленькие интерфейсы лучше одного «толстого» (принцип разделения интерфейсов).
6. **Почему `Items` — `IReadOnlyList`?** — Инкапсуляция: внешний код не может обойти метод `Add` и испортить корзину.
7. **Почему `decimal`, а не `double`, для цены?** — `double` хранит числа в двоичном виде и даёт ошибки округления (0.1 + 0.2 ≠ 0.3); для денег это недопустимо.
8. **Что даёт `item is IDownloadable file`?** — Проверку типа и приведение в одной строке; без него понадобились бы `is` + `as` или явное приведение.
