## 1. Немного теории

Классы в программе связаны друг с другом. Виды связей, от слабой к сильной:

| Связь | Смысл | Кто создаёт «часть» | Что с частью, если удалить «целое» | Пример в проекте |
|---|---|---|---|---|
| **Ассоциация** | объекты знают друг о друге и пользуются друг другом | каждый создан сам по себе | ничего, «целого» нет вообще | Студент — Преподаватель |
| **Агрегация** | целое **имеет** части, но не владеет ими | снаружи, передаётся готовой | остаётся жить | Команда — Игроки |
| **Композиция** | целое **состоит** из частей | само целое (`new` внутри) | исчезает вместе с целым | Автомобиль — Двигатель |
| **Наследование** | один класс **является** разновидностью другого | — | — | Птица — Животное |

Как отличить агрегацию от композиции в коде — два вопроса:

1. **Кто пишет `new`?** Если часть приходит готовой через конструктор или метод — агрегация. Если целое создаёт её само — композиция.
2. **Есть ли на часть ссылки снаружи?** При композиции часть спрятана в `private`-поле и наружу не отдаётся.

Агрегация и композиция — частные случаи ассоциации (отношение «имеет», *has-a*). Наследование — отношение «является» (*is-a*).

На UML-диаграммах: ассоциация — простая линия, агрегация — линия с **пустым** ромбом у целого, композиция — с **закрашенным** ромбом, наследование — стрелка с пустым треугольником к предку.

В C# нет слов «агрегация» или «композиция» — это способ **организовать** код, а не конструкции языка. Сборщик мусора удаляет объект, когда на него не осталось ссылок: поэтому «часть» при композиции исчезает вместе с целым (ссылка была только у него), а при агрегации остаётся (ссылки есть снаружи).

## 2. `Association.cs` — ассоциация

```csharp
1   using System;
3   namespace ClassRelations
18      public class Teacher
20          public string Name { get; }
22          public Teacher(string name)
24              Name = name;
31          public void CheckHomework(Student student)
33              Console.WriteLine(Name + " проверяет работу студента " + student.Name);
```

- **стр. 1** — `Console`.
- **стр. 18** — класс «Преподаватель».
- **стр. 20** — автосвойство только для чтения: задаётся в конструкторе и не меняется.
- **стр. 22–24** — конструктор сохраняет имя.
- **стр. 31** — студент приходит **параметром метода**: преподаватель пользуется им только внутри вызова и не хранит. Это самая слабая форма ассоциации.
- **стр. 33** — вывод.

```csharp
38      public class Student
40          public string Name { get; }
46          public Teacher Mentor { get; set; }
48          public Student(string name)
50              Name = name;
53          public void AskQuestion()
55              if (Mentor == null)
57                  Console.WriteLine(Name + ": мне некому задать вопрос");
61                  Console.WriteLine(Name + " задаёт вопрос преподавателю " + Mentor.Name);
```

- **стр. 46** — **ссылка на другой объект**. Признаки ассоциации: свойство с `set` (связь можно поменять) и может быть `null` (студент существует и без руководителя). Преподавателя студент не создаёт.
- **стр. 48–50** — в конструкторе руководитель не задаётся.
- **стр. 55–61** — если руководителя нет — одно сообщение, иначе студент обращается к объекту по ссылке (`Mentor.Name`).

```csharp
66      public static class AssociationDemo
68          public static void Run()
71              Teacher ivanov = new Teacher("Иванов И.И.");
72              Teacher petrova = new Teacher("Петрова А.С.");
73              Student student = new Student("Олег");
75              student.AskQuestion();
77              student.Mentor = ivanov;
78              student.AskQuestion();
79              ivanov.CheckHomework(student);
81              student.Mentor = petrova;
82              student.AskQuestion();
84              student.Mentor = null;
85–86           Console.WriteLine("Связь разорвана, но оба объекта существуют: " + student.Name + " и " + petrova.Name);
```

- **стр. 66** — статический класс с демонстрацией; вызывается из `Program.cs`.
- **стр. 71–73** — все объекты создаются **независимо**.
- **стр. 75** — руководителя ещё нет.
- **стр. 77–79** — установили связь; оба объекта пользуются друг другом.
- **стр. 81–82** — связь легко поменять.
- **стр. 84–86** — и разорвать; оба объекта продолжают существовать.

## 3. `Aggregation.cs` — агрегация

```csharp
1   using System;
2   using System.Collections.Generic;
4   namespace ClassRelations
19      public class Player
21          public string Name { get; }
23          public Player(string name)
25              Name = name;
```

- **стр. 2** — `List<T>`.
- **стр. 19–25** — «часть»: игрок с именем. О команде ничего не знает.

```csharp
30      public class Team
32          public string Title { get; }
35          private readonly List<Player> players = new List<Player>();
37          public Team(string title)
39              Title = title;
46          public void AddPlayer(Player player)
48              players.Add(player);
51          public void RemovePlayer(Player player)
53              players.Remove(player);
```

- **стр. 30** — «целое»: команда.
- **стр. 35** — команда хранит **список ссылок** на игроков. `readonly` — сам список заменить нельзя, но его содержимое меняется.
- **стр. 46–48** — **главный признак агрегации**: игрок приходит **готовым снаружи**. В методе нет `new Player(...)`.
- **стр. 51–53** — игрока можно убрать из команды; сам объект при этом не уничтожается.

```csharp
56          public void PrintPlayers()
58              Console.Write("Команда «" + Title + "»: ");
59              if (players.Count == 0)
61                  Console.WriteLine("игроков нет");
62                  return;
65              List<string> names = new List<string>();
66              foreach (Player p in players)
68                  names.Add(p.Name);
70              Console.WriteLine(string.Join(", ", names));
```

- **стр. 58** — `Write` без перевода строки: продолжение будет на той же строке.
- **стр. 59–62** — пустая команда.
- **стр. 65–70** — собрать имена в список и вывести через запятую.

```csharp
74      public static class AggregationDemo
76          public static void Run()
79              Player anna = new Player("Анна");
80              Player boris = new Player("Борис");
81              Player vera = new Player("Вера");
83              Team tigers = new Team("Тигры");
84              tigers.AddPlayer(anna);
85              tigers.AddPlayer(boris);
86              tigers.PrintPlayers();
90              Team lions = new Team("Львы");
91              lions.AddPlayer(boris);
92              lions.AddPlayer(vera);
93              lions.PrintPlayers();
98              tigers = null;
99              Console.WriteLine("Команда «Тигры» распущена, а игроки остались: " + anna.Name + ", " + boris.Name);
100             lions.PrintPlayers();
```

- **стр. 79–81** — игроки существуют **до** всякой команды.
- **стр. 83–86** — команда получает готовых игроков.
- **стр. 90–93** — Борис входит **сразу в две команды**: часть не принадлежит целому эксклюзивно. При композиции так нельзя.
- **стр. 98** — «распускаем» команду: убираем единственную ссылку на неё; объект потом удалит сборщик мусора.
- **стр. 99–100** — игроки остались: на них есть ссылки в переменных и во второй команде.

## 4. `Composition.cs` — композиция

```csharp
1   using System;
3   namespace ClassRelations
18      public class Engine
20          public int Power { get; }
22          public Engine(int power)
24              Power = power;
27          public void Start()
29              Console.WriteLine("  двигатель (" + Power + " л.с.) запущен");
```

- **стр. 18–29** — «часть»: двигатель с мощностью и методом запуска.

```csharp
34      public class Car
36          public string Model { get; }
40          private readonly Engine engine;
46          public Car(string model, int enginePower)
48              Model = model;
49              engine = new Engine(enginePower);
```

- **стр. 40** — `private` — двигатель виден только внутри автомобиля; `readonly` — заменить его после создания нельзя.
- **стр. 46** — в конструктор приходит **не готовый двигатель, а число** (мощность).
- **стр. 49** — **главный признак композиции**: объект-часть создаётся здесь, внутри целого. Больше ни у кого ссылки на него нет.

```csharp
56          public void Start()
58              Console.WriteLine(Model + " заводится:");
59              engine.Start();
63          public int EnginePower
65              get { return engine.Power; }
```

- **стр. 56–59** — **делегирование**: автомобиль не делает работу сам, а поручает её своей части.
- **стр. 63–65** — наружу отдаются только сведения о двигателе (число), но не сам объект — иначе композиция превратилась бы в агрегацию.

```csharp
69      public static class CompositionDemo
71          public static void Run()
74              Car car = new Car("Лада Веста", 106);
75              car.Start();
76              Console.WriteLine("Мощность: " + car.EnginePower + " л.с.");
84              car = null;
85              Console.WriteLine("Автомобиля больше нет — и его двигателя тоже.");
```

- **стр. 74** — создаём только автомобиль; двигатель появляется внутри сам.
- **стр. 75–76** — работа через автомобиль.
- Между ними в файле стоит закомментированная строка `car.engine.Start();` — она не скомпилируется: поле закрытое.
- **стр. 84** — убрали ссылку на автомобиль. Сборщик мусора удалит и его, и двигатель: на двигатель больше никто не ссылается.

## 5. `InheritanceVsComposition.cs` — наследование или композиция

Цель работы требует привести примеры наследования и композиции и сравнить их. Одна задача («объекты двигаются по-разному») решена двумя способами.

### 5.1. Наследование

```csharp
18      public class Animal
20          public string Name { get; }
22          public Animal(string name)
24              Name = name;
28          public virtual void Move()
30              Console.WriteLine(Name + " идёт");
35      public class Bird : Animal
37          public Bird(string name) : base(name)
41          public override void Move()
43              Console.WriteLine(Name + " летит");
```

- **стр. 18** — базовый класс.
- **стр. 28** — `virtual` — наследник может заменить метод своим.
- **стр. 35** — `Bird : Animal` — птица **является** животным и получает всё, что есть у предка.
- **стр. 37** — `: base(name)` — вызвать конструктор базового класса; тело пустое.
- **стр. 41** — `override` — своя версия метода.

### 5.2. Композиция

```csharp
50      public interface IMovement
52          string Describe();
55      public class Wheels : IMovement
57          public string Describe() { return "едет на колёсах"; }
60      public class Propeller : IMovement
62          public string Describe() { return "летит на пропеллерах"; }
```

- **стр. 50–52** — способ передвижения вынесен в отдельный интерфейс.
- **стр. 55–62** — две реализации.

```csharp
69      public class Robot
71          public string Name { get; }
74          public IMovement Movement { get; set; }
76          public Robot(string name, IMovement movement)
78              Name = name;
79              Movement = movement;
82          public void Move()
84              Console.WriteLine(Name + " " + Movement.Describe());
```

- **стр. 69** — робот **ни от кого не наследуется**.
- **стр. 74** — внутри него лежит объект-«способ движения». Свойство с `set` — поведение можно заменить **во время работы**.
- **стр. 76–79** — способ движения передаётся в конструктор.
- **стр. 82–84** — делегирование: работу выполняет вложенный объект.

Строго говоря, раз способ движения приходит снаружи, это агрегация. Но в литературе выражение «композиция вместо наследования» означает именно такой приём — собирать поведение из объектов-частей, а не наследовать.

### 5.3. Демонстрация

```csharp
88      public static class InheritanceVsCompositionDemo
90          public static void Run()
93              Animal[] animals = { new Animal("Кот"), new Bird("Воробей") };
94              foreach (Animal animal in animals)
96                  animal.Move();
102             Robot robot = new Robot("Робот", new Wheels());
103             robot.Move();
104             robot.Movement = new Propeller();
105             robot.Move();
107–118         (вывод плюсов и минусов, список языков)
```

- **стр. 93–96** — полиморфизм: в массиве типа `Animal` лежат разные объекты, и `Move()` у каждого свой. Но воробей всегда летает — поведение «зашито» в класс.
- **стр. 102–105** — тот же объект-робот сначала едет, потом летит: поведение заменено на ходу.
- **стр. 107–118** — текст для отчёта: плюсы и минусы обоих подходов и языки без наследования классов (Go, Rust).

| | Наследование | Композиция |
|---|---|---|
| Плюсы | мало кода; готовый полиморфизм; наследник сразу умеет всё, что предок | части легко заменять, даже во время работы; слабая связанность; части тестируются отдельно |
| Минусы | сильная связь с предком; только один базовый класс; поведение нельзя сменить на ходу | больше классов; работу нужно вручную передавать части |

## 7. Важные моменты (вопросы на защите)

1. **Чем агрегация отличается от композиции?** — При агрегации часть создаётся снаружи и переживает целое; при композиции целое создаёт часть само, и без него она не существует.
2. **Как это видно в коде?** — Агрегация: `AddPlayer(Player player)` — готовый объект в параметре. Композиция: `engine = new Engine(...)` в конструкторе и `private`-поле.
3. **Что будет, если `Car` вернёт наружу сам объект `Engine`?** — На двигатель появятся внешние ссылки, он сможет пережить автомобиль — композиция нарушится.
4. **Может ли часть входить в два целых?** — При агрегации да (Борис в двух командах), при композиции нет.
5. **Что такое делегирование?** — Объект поручает выполнение работы другому объекту, который в нём хранится (`car.Start()` вызывает `engine.Start()`).
6. **Почему советуют «предпочитать композицию наследованию»?** — Меньше связанность, поведение можно менять на ходу, нет ограничения в один базовый класс.
7. **Когда наследование всё же уместно?** — Когда действительно выполняется отношение «является» и наследник может полностью заменить предка (принцип Лисков, задание по SOLID).
8. **Как связи изображаются в UML?** — Ассоциация — линия, агрегация — пустой ромб у целого, композиция — закрашенный ромб, наследование — стрелка с треугольником.
